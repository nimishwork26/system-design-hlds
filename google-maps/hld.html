A global mapping platform serving 1B+ users — turn-by-turn routing, real-time traffic, map tile serving, and location search at planetary scale.

1. Requirements

Functional
  • Map tile display — render any location at any zoom level
  • Location search — find places by name or category near a point
  • Turn-by-turn directions — driving, walking, transit between two points
  • ETA — estimated arrival time accounting for current traffic
  • Live traffic overlay — see real-time congestion on the map
  • Route recalculation — re-route when user deviates
Non-Functional
  • Route calculation <200ms p99 globally
  • Tile serve <50ms for cached tiles
  • Traffic freshness <5 min lag end-to-end
  • 99.99% availability (4.3 min downtime/month)
  • Eventual consistency for traffic; strong consistency for route existence (no routing over closed roads)
Out of Scope
  • Street View imagery pipeline
  • Transit schedule management
  • Business listing / Google Places backend
  • Satellite / aerial imagery processing

3. Naive Design

Start with the simplest possible system: one API server backed by a map database. The server runs Dijkstra for routing, queries the DB for search, and renders tiles on demand from raw geometry data.

(roads, POIs, geometry)"]

This works in development. Here's where it fails at production scale:

Break 1 — Routing is 10× too slow

Dijkstra on 100M nodes = ~2s. Need <200ms. Can't just add servers — it's algorithmic.

Break 2 — Can't render tiles on demand

Tile rendering takes 50–200ms. 58K req/sec = 5,800 dedicated render threads. Latency before the tile even leaves the datacenter.

Break 3 — Traffic data is a firehose

100M GPS probes/min. Any DB that stores raw pings requires 3.5 PB/day of storage.

Break 4 — Search needs two indexes at once

"Coffee near me" needs text relevance AND spatial proximity. SQL can't rank by both simultaneously.

Break 5 — Map updates cascade everywhere

A new road affects tiles, the routing graph, and the search index. Synchronous updates across all three take hours.

4. Routing Speed

The Problem

The global road network has ~100 million nodes and ~200 million edges. Dijkstra's algorithm runs in O(V log V + E) — roughly 2 seconds per route query on modern hardware. With 5,800 routes/second, that's 11,600 CPU cores needed — and the latency still misses the 200ms SLA by 10×.

What are the options?

Fails
Standard Dijkstra — Guaranteed optimal path, simple to implement, well-understood. Every CS graduate can reason about it.

Visits every node in the shortest-path tree before finding the destination. On 100M nodes, that's ~2 seconds even on a 2024 server. At 5,800 concurrent queries, the math doesn't close.
Fails
A* with straight-line distance heuristic — Guides the search toward the destination using geographic distance as a lower-bound estimate. Gives a 2–4× speedup over Dijkstra in practice.

Still visits millions of nodes for cross-city or cross-country routes. NYC → LA via A*: still ~800ms. We need 200ms.
Partial
Bidirectional A* — Run search simultaneously from source and destination; stop when the two frontiers meet. Reduces explored nodes by ~75%, reaching ~500ms for long routes.

Better, but still misses the SLA for global routes. Correctness is also tricky: the meeting criterion for bidirectional search requires careful handling to guarantee optimality.
Decision
Contraction Hierarchies (CH) — An offline preprocessing step that assigns an "importance" rank to every node (highways are important; residential cul-de-sacs are not). Low-importance nodes are "contracted" — removed from the graph and replaced with shortcut edges. At query time, bidirectional search only travels upward through importance levels, exploring ~5,000 nodes instead of 50 million. Result: 5–20ms per route, a ~1000× speedup over Dijkstra.
Decision

Build a Contraction Hierarchy in an offline preprocessing phase (~4 hours for the global graph). The augmented graph is serialized into a custom binary format (~8GB) and loaded into RAM on every routing server at startup. Route queries run bidirectional upward search on this augmented graph in 5–20ms. The preprocessing is re-run whenever the road network changes significantly (daily for minor updates, weekly for full global rebuilds).

The aha moment: CH works because real road networks have natural hierarchies — most long trips eventually use highways or major arterials. Contracting a cul-de-sac adds exactly one shortcut edge (its two neighbors become directly connected) and removes that node from all future queries. After contracting the bottom 90% of nodes by importance, the remaining query graph is tiny. The structure of actual roads is what makes the 1000× gain possible.

CH Preprocessing pipeline

1
Assign importance scores
Score each node by: edge difference (shortcuts needed minus edges removed), road hierarchy level (motorway > residential), and contractor neighbor count. Lower score = contracts first.
2
Contract nodes in ascending importance order
Remove least-important node. For every pair of its neighbors (u, v), if the path through this node is a unique shortest path, add a shortcut edge u→v with combined weight. Mark node as contracted.
3
Serialize augmented graph
Binary format: node_id → {level, lat, lng, outgoing_edges[]}. ~8GB for global network. Loaded at startup in ~45 seconds. Held in RAM on all routing servers.
4
Query: bidirectional upward search
From source and destination, only relax edges going to higher-importance nodes. When both frontiers have settled the same top node, extract the path. ~5,000 nodes explored vs 50M for plain Dijkstra.

5. Map Tile Serving

The Problem

Rendering a single map tile from raw vector geometry takes 50–200ms of CPU time. Google Maps sees ~58,000 tile requests per second at peak. On-demand rendering would require ~5,800 dedicated render server cores just to handle throughput — and p99 tile latency would be 200ms+ before the response even starts transmitting.

Fails
On-demand rendering — Always shows the freshest map data; zero storage overhead; supports infinite style variations (dark mode, accessibility themes).

At 58K req/sec and 100ms render time, we need 5,800 concurrent render threads. CPU cost is prohibitive. More critically, tile latency at p99 would be 200ms+ before the payload even starts transmitting — CDN edge nodes would see nothing to cache.
Partial
On-demand rendering + aggressive caching (Varnish/Redis) — Cache rendered tiles by (x, y, zoom, style) key. Downtown Manhattan at zoom 15 gets served from cache 99% of the time.

The long tail is enormous: Earth at zoom level 20 has 274 trillion possible tile positions. Cold-cache penalty is 100–200ms. Worse: cache invalidation when map data changes (road renamed, new building) requires identifying and purging thousands of affected tiles across potentially hundreds of CDN PoPs simultaneously.
Decision
Pre-render all tiles at build time + global CDN — During the map data build pipeline, pre-render every non-empty tile at every zoom level (0–20). Store in distributed object storage (Google Cloud Storage). Tiles are immutable — addressed by /v{map_version}/{zoom}/{x}/{y}.pbf. When map changes, a new version is generated; CDN cache keys change atomically with the version bump. Old tiles remain cached for clients still on the prior version.
Decision

Pre-render tiles during the versioned map build. At zoom 0–15, the total non-empty tile count is ~340M — about 170GB as compressed vector tiles. Higher zoom levels are ~99% empty (ocean, ice, desert) and rendered sparsely. Global CDN achieves 99.8%+ cache hit rate, meaning only ~116 tile requests/second ever touch origin servers. New version promotion is instantaneous from the user's perspective — clients request tiles with the new version token once their app refreshes.

Vector Tiles vs Raster

Google serves vector tiles (.pbf — Protocol Buffer format) rather than PNG images. The client renders them locally in WebGL/Metal. Benefits: 10× smaller storage, smooth zoom transitions without re-requesting tiles, dynamic style application (dark mode, accessibility) without new round trips, and text/labels rendered in the client's locale. The server never knows what the rendered tile looks like — only the geometry data.

6. Real-time Traffic

The Problem

Google Maps collects anonymous GPS probes from ~1 billion Android devices. At just 10% reporting rate in navigation mode, that's ~100 million pings per minute = ~1.7 million writes per second. Storing raw GPS data is physically impossible: 24 bytes/ping × 100M/min × 1440 min/day = 3.5 PB/day. Yet we need traffic data fresh enough to give accurate ETAs.

Fails
Store all raw GPS pings in a database — Complete audit trail; enables ML training on raw traces; allows future replay for any traffic question.

At 1.7M writes/sec, no off-the-shelf database handles this rate. Even Cassandra (optimized for writes) at 100K writes/sec per node requires 17 nodes just for ingestion. Storage: 3.5 PB/day, or $1M+/day in cloud object storage at list prices. Aggregating segment speeds from raw pings at query time would take minutes.
Fails
Random sampling — store only 1% of probes — Reduces write volume 100× to ~17K writes/sec. Manageable with a standard database.

Works on major highways with thousands of probes per minute. Catastrophically fails on less-traveled roads: a 3-car accident on a side street may generate only 2–3 probes per minute — 1% sampling means 0 data points. Traffic quality degrades exactly where incidents matter most.
Decision
Full ingestion → stream processing → aggregate to road segments — Kafka absorbs all probes at full rate (~1.7M/sec). A fleet of stream processors (Dataflow/Flink) map-match each probe to a road segment and compute per-segment average speeds over rolling 5-minute windows. Only the derived segment speeds (~10M segments × one float = 40MB per snapshot) are persisted to Bigtable. Raw pings never touch persistent storage.
Decision

Kafka partitioned by geographic tile absorbs the firehose. Stream processors run Hidden Markov Model map-matching — snapping noisy GPS coordinates (±5–20m error) to the most likely sequence of road segments. Per-segment median speeds are computed in 5-minute sliding windows and written to Bigtable with key segment_id#timestamp. Traffic is fresh within 2–3 minutes of real-world conditions. Raw pings are never stored; the entire pipeline operates as a stateless transformation.

Map-matching is non-trivial: GPS accuracy is ±5–20m — enough to misidentify the road on parallel streets, near multi-level interchanges, or inside tunnels. A Hidden Markov Model treats map-matching as a sequence problem: given a sequence of noisy GPS points, find the most likely sequence of road segments, considering both point-to-road distance and transition probabilities between adjacent segments. Without HMM, ~15% of pings would be assigned to the wrong road segment, corrupting speed estimates.

Traffic pipeline

1
GPS probe emitted
Android device in navigation mode sends (lat, lng, speed, bearing, timestamp) every 5–30 seconds. Anonymized before transmission. Bundled with other telemetry to minimize battery drain.
2
Kafka ingestion
Published to a Kafka topic partitioned by geographic tile (S2 cell). Ensures probes for the same road segment go to the same consumer partition — locality reduces cross-partition joins during map-matching.
3
Map-matching (HMM)
Stream processor (Dataflow) assigns each probe to the most likely road segment using a Hidden Markov Model. Handles GPS noise, tunnel gaps, and multi-level roads (overpass vs underpass).
4
Speed aggregation
Per-segment median speed computed over a 5-minute sliding window. Statistical outliers filtered. Result: ~10M (segment_id, speed_mph, confidence) records per snapshot.
5
Write to Bigtable + inject into routing
Segment speeds written to Bigtable for historical analysis. Also hot-patched into the in-memory routing graph as time-dependent edge weights. ETA service reads Bigtable for its ML model features.

7. Location Search (Geocoding)

The Problem

"Coffee shops near Union Square" requires text relevance (is this a coffee shop?) and spatial proximity (is it near Union Square?) simultaneously. A standard inverted text index ranks by text score and can't efficiently pre-filter by geography. A spatial index filters by distance but can't rank by text relevance. Combining both in SQL — even with PostGIS — produces plans that degrade to full scans at 200M POIs.

Fails
SQL full-text search + PostGIS spatial filter — Single system, familiar tooling, ACID transactions for POI data updates. PostgreSQL can do tsvector full-text search AND ST_DWithin with a GiST spatial index.

At 200M POIs, combining tsvector ranking with spatial filtering creates a query planner nightmare. Postgres must choose between the spatial index (good for tight radii) or the text index (good for rare terms) — it can't efficiently use both simultaneously. Query times at 200M rows: 500ms+. Under write load (25M map updates/day), index maintenance degrades query performance further.
Partial
Elasticsearch with geo_distance filter — Excellent BM25 text scoring + geo_distance post-filter. Industry-standard approach for search-with-location. Scales to hundreds of millions of documents.

geo_distance is a post-filter: Elasticsearch first retrieves all text matches (potentially 10M "coffee" results globally), then filters by radius. For broad category searches, this is extremely expensive. Can't efficiently handle "within this polygon" queries (city boundaries, neighborhoods) — geo_shape queries require heavy computation.
Decision
Elasticsearch + S2 cell index tokens — Each POI is indexed with its S2 cell token at multiple levels (coarse city → fine block). Spatial pre-filtering is a prefix scan on S2 cell IDs — a near-O(1) Lucene term lookup, not a bounding-box computation. Combined with BM25 text scoring and distance-decay function scoring. End-to-end: 30–50ms for 200M POIs.
Decision

Every POI is indexed in Elasticsearch with: (1) text fields (name, category, address) for BM25 ranking, (2) a geo_point field for distance-decay scoring, (3) S2 cell tokens at levels 10–15 as keyword fields for instant spatial pre-filtering. A search query first issues a terms query on S2 cell tokens covering the search radius — this reduces 200M POIs to ~10K candidates in sub-millisecond time. BM25 text scoring runs on just those 10K candidates. Final ranking combines text relevance + distance decay. Geocoding (address → lat/lng) uses a separate structured address trie.

S2 cells: Google's S2 geometry library maps Earth's surface onto a space-filling Hilbert curve, creating a hierarchy of square cells at 31 levels of precision. Adjacent cells have numerically adjacent IDs, so a geographic area translates to a set of cell ID ranges — a prefix scan in Lucene. Level 10 ≈ city district (1.27 km²), Level 13 ≈ neighborhood block (153 m²). Indexing each POI at 4–5 levels covers both broad and narrow search radii without re-indexing.

8. Map Data Updates

The Problem

Google processes ~25 million map changes per day — new roads, closures, speed limit changes, business openings. Each change requires updates to three separate derived systems with different rebuild times: tile re-rendering (hours for a major area), CH graph rebuild (4 hours globally), and Elasticsearch index update (minutes). Synchronous all-or-nothing updates block serving. Independent async updates create dangerous inconsistencies — routing over a road the tile shows as closed.

Fails
Synchronous update across all three systems — Strong consistency; users never see a discrepancy between the map, routing, and search.

Tile re-rendering for a major road change affects thousands of tiles at multiple zoom levels: hours of processing. Routing graph rebuild: 4 hours. During this window, the entire map serving would be blocked. Any failure in one system rolls back all three. Completely incompatible with 99.99% availability SLA.
Partial
Each service subscribes independently to a change feed — Tiles, routing, and search each consume a Pub/Sub change log and update themselves asynchronously. No blocking. Each service is independently available.

Creates temporary windows where routing navigates over a road the tile shows as closed (or vice versa). In the worst case, a user is directed down a road that visually appears blocked. The inconsistency window can last hours if the tile rebuild is delayed. User-visible and potentially dangerous.
Decision
Immutable versioned map snapshots with atomic version promotion — Map data is versioned (v1001, v1002, ...). A build pipeline assembles a new snapshot from batched changes, then builds all three derived systems (tiles, CH graph, Elasticsearch index) against that snapshot in parallel. A single atomic version pointer is promoted only after all three are ready. All serving systems switch to the new version simultaneously.
Decision

Map source data is stored in Spanner as immutable versioned rows. The build pipeline runs continuously, batching changes into new snapshots every ~15 minutes. Tiles, graph, and index are rebuilt against the new snapshot in parallel. A version gate in the serving layer — a single Spanner read of the current_version row — atomically switches all three when the build completes. Old snapshots are retained for 24 hours for instant rollback. Emergency road closures use a fast-path: direct hot-patch to the live routing graph (infinite edge weight for closed road) + immediate traffic pipeline update, while the full rebuild completes asynchronously.

Not perfectly real-time: The versioned snapshot approach means confirmed map changes go live 15–30 minutes later. This is acceptable for most changes. The emergency hot-patch path covers time-sensitive closures. Traffic-driven tile overlays (congestion coloring) update within 2–3 minutes via the stream processing pipeline, independent of the snapshot cycle.

9. API Design

Only the non-obvious endpoints — the ones where the design choice requires explanation.

Route calculation

GET /v1/directions
  origin=37.7749,-122.4194        // or place_id:ChIJ...
  destination=34.0522,-118.2437
  mode=driving|walking|transit
  departure_time=1735000000       // unix timestamp — enables predictive ETA
  alternatives=true               // return up to 3 routes
Why departure_time? Traffic patterns vary by hour and day. A Monday 8am route differs significantly from a Sunday 2pm route. The routing engine uses historical traffic profiles (built from 90 days of segment-speed history) to assign time-dependent edge weights. Specifying departure_time in the future enables planning ("leave in 2 hours") with historically-accurate ETAs — not just current congestion.

Tile serving

GET /maps/vt
  x={tile_x}&y={tile_y}&z={zoom}
  v={map_version}                  // enables aggressive CDN caching
  style={style_id}                 // dark, satellite, accessibility
  lang={locale}                    // label language (rendered client-side for vector)
Why include the map version in the URL? Tile URLs are immutable — same URL always returns the same bytes. This allows Cache-Control: max-age=86400, immutable with no stale-data risk. When the map version changes, new URLs are used. Old tiles remain valid for clients that haven't refreshed their version token yet, so there's no thundering herd on version promotion.

Location search

GET /v1/place/search
  query=coffee
  location=37.7749,-122.4194      // anchor point for S2 cell selection
  radius=2000                      // meters → maps to S2 level
  max_results=20
  page_token=eyJ...               // cursor-based, not offset — consistent under writes
Why cursor-based pagination? Offset-based pagination (page=2&size=20) is unstable under concurrent writes to the POI index: a new business indexed between page 1 and page 2 requests causes a result to appear on both pages. A cursor encodes the last-seen document ID, ensuring consistent pagination regardless of concurrent index changes.

ETA (lightweight routing)

GET /v1/eta
  origin=37.7749,-122.4194
  destination=34.0522,-118.2437
  departure_time=1735000000
ETA vs full directions: ETA is a lighter call — it runs CH routing but skips the path reconstruction step (building the turn-by-turn polyline). This matters because ride-hailing and delivery apps call ETA for every driver-to-destination pair (O(drivers × destinations)), while users call full directions only once per trip. Omitting polyline serialization cuts response time and payload size by ~40%.

12. Failure & Scale

Routing server failure

Routing server crashes mid-query

The CH graph is loaded in RAM at startup — routing servers are stateless. Load balancer health checks remove a crashed instance within 10–30 seconds. Other instances handle requests immediately with no shared state to synchronize. At 70% target utilization, the fleet absorbs a 30% capacity reduction with <50% latency increase. Cold start from GCS binary: ~45 seconds. Autoscaling triggers at 80% utilization.

CDN cache invalidation storm

New map version invalidates widely-cached tiles

When a new map version promotes, tile URL paths change. A thundering herd hits origin GCS servers. Mitigation: stagger version rollout by region (US → Europe → APAC, 30-minute intervals). Pre-warm CDN PoPs with the top-1M most-requested tiles before promoting the version token. New clients get the new version; existing sessions continue with old version URLs until their next tile viewport pan/zoom, spreading the cache-fill over hours rather than seconds.

Kafka consumer lag spike

GPS probe rate spikes 10× during a major event

Kafka partitions absorb the burst — producers never block. Consumer lag increases, meaning traffic freshness degrades from 2 minutes toward 10 minutes. This is acceptable (graceful degradation). The system emits a traffic_data_age metric; ETA service automatically increases its uncertainty bound when data exceeds 5 minutes old. Autoscaling adds Dataflow workers to drain the backlog; typically cleared within 5–8 minutes.

Map build pipeline failure

Build pipeline crashes during version construction

The version pointer is only promoted after all three derived systems complete successfully. A failed build leaves the pointer on the previous snapshot — users see a slightly older map (15–30 minutes behind). The failed build retries from the last checkpoint. Since builds are idempotent (same input snapshot → same output), retries are safe. Previous snapshot retained for 24 hours supports instant rollback if a bad build is accidentally promoted.
