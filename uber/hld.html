3. Start Simple — Then Find What Breaks

Before introducing any specific technology, let's sketch the simplest design that could possibly work and stress-test it.

The simplest design

Two clients (rider app, driver app) → an API server → a single relational database. Driver apps POST their location every 5 seconds. When a rider requests a ride, the server queries the DB for nearby available drivers and assigns one.

Where does it break?

Break Point 1

5M drivers × 1 update/5s = 1M writes/sec into our database. PostgreSQL handles ~10K writes/sec comfortably. We're 100× over that limit before a single rider has requested anything.

Break Point 2

Finding nearby drivers requires a proximity query over 5M rows every time a rider requests a ride. Without spatial indexing this is a full table scan. Even with indexing, the query needs to be sub-100ms at hundreds of requests/sec.

Break Point 3

If two server instances both pick the same available driver for two different riders simultaneously — we have a double assignment. One rider's driver never shows up. Critical correctness failure.

Break Point 4

How does the rider see the driver moving on the map? If we rely on the rider polling "where is my driver?" every 5 seconds, that's 315K concurrent trips × 12 polls/min = 3.8M requests/min of mostly empty responses.

These four break points become our design agenda. Let's solve each one in order.

4. Problem: Tracking 5M Driver Locations at 1M Writes/Sec

The Problem

We need to: (a) ingest 1M location updates/sec with very low write latency, and (b) answer "which drivers are within 5km of this point?" in under 100ms.

Option exploration

Fails
Write directly to PostgreSQL/DynamoDB. PostgreSQL handles ~10K writes/sec. We need 100× more. DynamoDB on-demand at 1M writes/sec would cost $200K+/day in write capacity. Even if we could afford it, proximity queries on a table of 5M rows are slow without spatial indexing — and re-indexing during a write storm is expensive.
Partial
Batch writes + PostGIS spatial index. Aggregate updates over 5–10 second windows, then batch-insert. PostGIS adds O(log n) proximity queries. Write throughput is now manageable. But: location data now lags reality by the batch window — every driver's position is 5–10s stale. This degrades matching quality and ETA accuracy. Also doesn't handle the sheer ingestion rate cleanly.
Decision
Redis Geo as the live driver index.
  • GEOADD drivers:nyc lat lng driver_id — encodes coordinates as a 52-bit integer in a sorted set. O(log n) write. GEOADD overwrites the previous entry — so the index never accumulates stale positions.
  • GEOSEARCH drivers:nyc FROMLONLAT lng lat BYRADIUS 5 km ASC COUNT 10 — returns nearest drivers in sub-millisecond.
  • All 5M driver positions fit in ~500 MB of RAM. The index lives entirely in-memory.
Decision

Redis Geo for live driver positions. In-memory, geospatial commands built-in, GEOADD overwrites (no stale data accumulation), sub-ms query latency. If Redis restarts, positions repopulate within 5s as drivers resume pinging — no complex recovery.

New problem: Redis is ephemeral — what about trip history?

New Constraint

We need driver location history for billing disputes and trip reconstruction. Redis can't serve this — it's an in-memory cache, not a log. We need a durable store for the same 1M writes/sec stream.

Fails
Write synchronously to Redis + a durable DB on every ping. Now every location update blocks on two writes. If the DB write is slow, the ingestion pipeline backs up. We've coupled the latency of two systems together.
Decision
Publish to Kafka, consume async into Cassandra. The Location Service writes to Redis (fast, synchronous) and publishes an event to Kafka (also fast, fire-and-forget). A separate Cassandra consumer reads from Kafka and appends to the location history log. The ingestion path is never blocked by the history write.
Why Cassandra for history? Location history is an append-only, time-series workload — exactly what Cassandra's LSM-tree is optimized for. We partition by (driver_id) and cluster by recorded_at, so querying a driver's trip trace is a single-partition range scan. Cassandra scales horizontally by adding nodes with no re-sharding.

New problem: one global Redis or sharded by city?

New Constraint

With 5M drivers globally, a single Redis instance handles the memory (500 MB is fine) but creates a blast radius problem: a Redis failure, a surge in NYC, or a slow query in London affects the entire world.

Risky
One global Redis cluster. Simple operationally. But a network partition or crash takes down matching everywhere. Peak demand during a New York event slows queries for drivers in São Paulo. Violates data residency requirements in some regions.
Decision
Shard by city/metro. Each city has its own Redis key namespace: geo:drivers:nyc, geo:drivers:sf. Kafka topics are also partitioned by city: location.nyc. A failure in NYC doesn't affect London. Peak demand is isolated. Regulatory data-residency requirements are met naturally.
Adaptive ping rate (bonus): The driver app doesn't need to ping at a fixed 5-second interval. A stationary driver waiting for a request can ping every 15–30s. A driver moving at speed near a pending request pings every 2s. This cuts write volume significantly without hurting matching quality.

5. Problem: Finding the Best Available Driver

The Problem

A rider requests a ride. We need to find the best available driver nearby — quickly. "Best" is not just closest; it's a combination of ETA, rating, and vehicle type.

Spatial indexing: how do we define "nearby"?

A naive scan over all 5M drivers is O(n). We need a spatial index that reduces the candidate set to hundreds before any ranking computation.

Workable
Geohash. Encode latitude/longitude as a base-32 string. A common prefix = same area. Query a cell and its 8 neighbors. Simple and widely understood. Problem: rectangular cells have unequal neighbor distances — a cell in the corner is much farther from its neighbor than one on the edge. This creates inconsistent proximity behavior near cell boundaries.
Better
Google S2. Projects the Earth onto cube faces, subdivides hierarchically. Each cell is a 64-bit integer. Better coverage uniformity than Geohash. Problem: square cells still have unequal distances — diagonal neighbors are √2× further than edge neighbors. Early Uber used S2 for geofencing but not for real-time dispatch.
Decision
H3 (Uber's production choice). Hexagonal grid. A hexagon's center is equidistant from all 6 neighboring hexagon centers — no diagonal-vs-edge inconsistency. Level 9 cells are ≈175m across. When a ride is requested, compute the H3 cell for the pickup, query that cell + 6 neighbors. Candidate set shrinks from 5M to hundreds before any scoring.

Scoring candidates — what makes a driver "best"?

Straight-line distance is not ETA. In a dense city, the driver 800m away across a river might take 12 minutes while the driver 1.2km away on the same side of the river takes 4 minutes. The ranking must use road-network ETA, not Euclidean distance.
FactorWhy it matters
Road-network ETAPrimary signal. Uses a routing engine (OSRM or Uber's internal equivalent) — modified Dijkstra with contraction hierarchies. Each ETA query must resolve in <50ms to support hundreds of concurrent dispatch decisions.
Driver ratingPrefers highly-rated drivers for quality, especially on premium tiers.
Acceptance rateAvoid offering to drivers who frequently reject — they add latency to the cascade.
Vehicle type matchA UberX request shouldn't be offered to an Uber Black driver if X drivers are nearby.

GPS accuracy issue

In dense urban areas, GPS errors of 50–100m are common due to building reflections. A driver showing as "across the street" might actually be a block away, or on a different floor of a parking garage.

Naive
Use raw GPS coordinates directly. Matching based on incorrect positions leads to wrong ETAs and drivers being routed inefficiently.
Decision
Map-matching via Hidden Markov Models. Snap raw GPS to the most probable road segment given the sequence of observations. Eliminates impossible positions (middle of a building, river). Additionally, use predictive positioning: extrapolate current position from last known heading + speed. At 60 km/h, a driver moves 83m in 5s — predictive positioning reduces effective staleness to <10m.
Decision

H3 cells for proximity filtering → road-network ETA for ranking → top candidate offered the ride. This is the Dispatch Service: it consumes a ride request, queries Redis Geo using H3 cell + neighbors, scores candidates by ETA + rating, selects the best available driver.

6. Problem: One Driver Must Only Be Assigned to One Rider

The Problem

We'll run multiple Dispatch Service instances for scalability. Two instances can simultaneously query Redis, get the same driver as the top candidate, and both attempt to assign them. Without a coordination mechanism, one rider's driver will vanish.

Fails
Application-level lock (in-memory). Each Dispatch instance maintains a set of "locked drivers" in its own memory. Instance A locks driver 42, but Instance B has no idea — it locks driver 42 too. Race condition guaranteed across processes. Lock state is also lost if the service crashes.
Better
Database compare-and-swap on driver status. Driver has a status field: available → outstanding_request → on_trip. Use an atomic CAS update: UPDATE drivers SET status='outstanding_request' WHERE id=42 AND status='available'. Only one caller gets the successful update. Problem: we need a timeout — if the driver doesn't respond in 10s, who resets the status back to available? The timeout logic lives in-memory and is lost if the service restarts. Driver can get stuck in outstanding_request forever.
Decision
Redis SETNX with TTL. SET driver:42:lock 1 EX 10 NX — atomic, only one caller wins the lock, auto-expires after 10 seconds whether the service crashes or the driver ignores the offer. No manual cleanup. Multiple Dispatch instances race safely — exactly one wins.
Decision

Acquire SETNX driver:{id}:lock EX 10 before sending an offer. If the lock fails (another instance already grabbed it), try the next candidate. If the driver accepts within 10s, transition them to on_trip in the DB. If they reject or ignore — lock auto-expires, driver becomes available again automatically.

7. Problem: The Matching Cascade Must Survive Service Crashes

The Problem

The matching process is a multi-step workflow: lock driver → send offer → wait 10s for response → if rejected, try next driver → repeat until match or failure. Each step has a timeout and a retry. If the Dispatch Service crashes mid-workflow, a rider can be left waiting indefinitely with no driver being tried.

Fails
In-memory setTimeout. Works until the service restarts. Timer state is gone on crash. Rider is stranded. Works fine for a prototype, unacceptable in production.
Better
Kafka delayed message. After sending an offer, publish a message with a future timestamp. If the driver accepts before it's consumed, ignore it. Otherwise, consume it and try the next driver. More durable than in-memory. Problem: Kafka doesn't natively support per-message delays. You need a separate delay service or use scheduled messages — adds complexity without clean semantics.
Decision
Temporal durable workflow. The entire matching cascade is modeled as a Temporal Workflow. Temporal persists workflow state to durable storage and replays from the last checkpoint on crash. Built-in sleep and timeout primitives model the 10s wait naturally. 
workflow MatchRider(rideId):
  candidates = findNearbyDrivers(rideId)
  for driver in candidates:
    acquireLock(driver.id)             // activity
    sendOffer(driver.id, rideId)       // activity
    result = waitForResponse(10s)      // durable sleep
    if result == ACCEPTED: return success
    releaseLock(driver.id)
  fail("NO_DRIVER_AVAILABLE")
If the service crashes after sendOffer but before waitForResponse, Temporal replays from waitForResponse. No ride is lost.
Decision

Temporal orchestrates the matching cascade. Each step is a durable activity. Timeouts are modeled as workflow sleeps. A crash mid-match resumes from the last checkpoint automatically. This removes the need for manual retry queues or in-memory timers.

8. Problem: How Do Riders See the Driver Moving?

The Problem

During a trip, the rider's app needs to show the driver's position updating every 5 seconds. How does the update get from the driver's phone to the rider's screen?

Inefficient
Rider app polls the server every 5s. At 315K concurrent trips, that's 315K GET requests every 5 seconds = 63K requests/sec of mostly empty responses (driver position hasn't changed yet). Every response is a wasted round-trip. Latency is up to 5s behind reality.
Decision
WebSocket connection opened when the ride starts. Server pushes driver position updates as they arrive from Location Service. No wasted polling. Update delivered in ~50ms vs up to 5s. The connection is closed when the trip ends.

New problem: routing pushes across 10M WebSocket connections

New Constraint

At 10M concurrent connections, we need ~1,000 stateful WebSocket servers (10K connections each). When the Dispatch Service needs to push a driver offer to a specific driver, which server holds their connection? If we send it to the wrong server, the message is silently dropped.

Bottleneck
Central registry (ZooKeeper / Redis hash). Map user_id → server_id in a shared store. Any service can look up which server to route to. Problem: this becomes a centralized coordination bottleneck. Every message dispatch requires a registry lookup. ZooKeeper under high write volume becomes a chokepoint. Adds a hop of latency to every push.
Decision
Ringpop (Uber's custom consistent hashing layer).
  • Consistent hashing maps each H3 cell ID to an owning Dispatch node. Any service can compute the correct node locally — no registry lookup.
  • SWIM gossip protocol propagates node health changes peer-to-peer. No central coordinator. A crashed node is detected and its cells are redistributed automatically.
  • Transparent forwarding — if a request arrives at the wrong node, it's forwarded to the correct owner.
Decision

WebSockets for live trip updates + Ringpop for routing pushes to the correct server. The WebSocket gateway cluster is self-organizing. No centralized coordinator. Decentralized failure detection. Scales horizontally by adding nodes.

9. API Design

With the core decisions made, the API falls out naturally. Two design choices worth calling out explicitly:

Why a separate fare estimate step?

If we accept POST /rides { pickup, dropoff, fare_amount }, a malicious client can pass fare_amount: $0.01. Instead:

POST /fare
  Body:  { pickup_lat, pickup_lng, dropoff_lat, dropoff_lng, ride_type }
  →      { fare_id, estimated_fare, eta, surge_multiplier }
  TTL:   2 minutes

The fare_id is stored server-side. When the rider confirms, they pass the fare_id — the server looks up the price, never trusting the client.

POST /rides { fare_id }
→ { ride_id, status: "searching" }
Server looks up fare from DB, creates trip record, publishes ride_requested to Kafka.
PATCH /rides/:id — driver accept/reject
Body: { action: "accept" | "reject" }
driver_id extracted from JWT — never from request body (prevents spoofing)
POST /drivers/location — called every ~5s
Body: { lat, lng, heading, speed }
driver_id from JWT — not body.
→ Location Service writes to Redis Geo + publishes to Kafka.

10. Final Architecture

Every component below was introduced to solve a specific problem above — not assumed upfront.

End-to-end request trace (rider books a ride)

1
Fare estimate
POST /fare → Fare Service calls Maps API → returns fare_id (stored in PG, 2-min TTL).
2
Rider confirms
POST /rides { fare_id } → Trip Service creates trip (SEARCHING) in PostgreSQL, publishes ride_requested to Kafka (city partition).
3
Dispatch Service kicks off Temporal workflow
Consumes Kafka event. Temporal workflow starts. GEOSEARCH Redis for H3 cell + neighbors. Score candidates by road ETA.
4
Lock + offer
SETNX driver:{id}:lock EX 10. Notification Service pushes offer via WebSocket/APNs/FCM. Temporal sleeps 10s durably.
5
Driver accepts
Trip Service updates status → DRIVER_ASSIGNED in PG. Rider gets WebSocket push with driver info and ETA.
6
Live tracking
Driver pings every ~5s → Location Service GEOADD to Redis (overwrites) + publishes to Kafka → Cassandra consumer appends. Rider's WebSocket receives pushes via Ringpop routing.
7
Trip ends
Trip Service computes fare_final (actual distance × time via Maps API). Writes to PG. Lock released. Both apps get TRIP_COMPLETED push.

12. Failure Modes — Stress Testing the Design

Every decision above should hold up under failure. Let's verify.

2015 Uber outage — the lesson that shaped this design: A database failover cascaded into 30 minutes of global downtime. The root cause: the geospatial driver index lived in the database. When the DB was unavailable, matching was completely dead. The fix: remove the database from the hot path entirely. The geo index now lives in Redis (in-memory). The DB is cold storage — never in the latency-critical matching path.

Scenario walkthroughs

Redis crashes mid-surge

All live driver positions are lost. Recovery: drivers resume pinging within 5s — Redis repopulates. No manual intervention. Trip records are unaffected (PostgreSQL). All active locks expired via TTL — no drivers stuck. Matching may degrade for ~5s, then fully recovers.

Dispatch Service crashes mid-workflow

Temporal replays the workflow from the last persisted activity. If it crashed after sendOffer, Temporal resumes at waitForResponse. The driver lock TTL auto-releases if it expires. No ride is lost, no driver double-assigned.

Driver ignores offer (no response in 10s)

Temporal's 10s sleep completes. releaseLock is called. Driver's lock expires. Temporal moves to the next candidate in the list. Rider is notified of updated ETA. If all candidates exhausted, radius is expanded and the workflow retries.

Event surge (concert ends, 50K riders simultaneously)

Kafka absorbs the spike — ride requests queue up in the city partition. Dispatch Service auto-scales based on consumer lag. Redis for that city sees higher query load but geo-sharding means only that city's shard is affected. Other cities are isolated.

Closing summary

The three hardest problems in this design are: (1) 1M location writes/sec — solved by treating Redis as an ephemeral live index and Cassandra as the durable append log; (2) preventing double assignment — solved with Redis SETNX TTL; (3) resilient matching workflow — solved with Temporal. Everything else follows from standard distributed systems patterns.
