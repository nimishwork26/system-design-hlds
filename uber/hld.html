Real-time ride-sharing: match riders with nearby drivers, track live location, manage trip lifecycle at global scale.

How to read this

Every component is arrived at through a problem — not listed upfront. Each section raises a constraint, explores options with trade-offs, then makes a decision. Read it the way you'd talk through a design in an interview.

3. Start Simple — Then Find What Breaks

The simplest possible design

Rider and driver apps talk to a single API server. Drivers POST their location every 5s. Rider requests a ride; server queries the DB for nearby available drivers and assigns one.

flowchart LR RA["Rider App"] --> API["API Server"] DA["Driver App"] --> API API --> DB[("Database")]

Where does it break?

Break #1

5M drivers × 1 update/5s = 1M writes/sec into our database. PostgreSQL handles ~10K writes/sec. We are 100× over the limit before any rider has requested a trip.

Break #2

Proximity queries over 5M rows on every ride request. Without spatial indexing this is a full table scan. With it, re-indexing during a 1M/s write storm is expensive.

Break #3

Two API server instances can simultaneously select the same driver for two different riders. One rider's driver never arrives. Critical correctness failure.

Break #4

If riders poll "where is my driver?" every 5s: 315K trips × 12 polls/min = 3.8M req/min of mostly empty responses.

These four break points become our design agenda — solved in order below.

4. Problem: 1M Location Writes/Sec

The Problem

Ingest 1M location updates/sec with low latency, and answer "which drivers are within 5km?" in under 100ms.

Fails
Write directly to PostgreSQL / DynamoDB. PG caps at ~10K writes/sec. DynamoDB at 1M writes/sec on-demand costs $200K+/day. Proximity queries on a live 5M-row table are slow and degrade under write pressure.
Partial
Batch writes + PostGIS. Aggregate over 5–10s windows, batch-insert. PostGIS gives O(log n) proximity queries. Write pressure drops. Problem: driver location now lags reality by the batch window — ETA accuracy degrades, matching quality drops.
Decision
Redis Geo. GEOADD drivers:nyc lat lng driver_id — O(log n) write, overwrites the previous position (no stale accumulation). GEOSEARCH returns nearest 10 drivers in sub-millisecond. All 5M positions fit in ~500 MB RAM. Repopulates from driver pings within 5s of a restart.

New problem: Redis is ephemeral — what about trip history?

Fails
Write synchronously to Redis + a durable DB on every ping. Couples ingestion latency to two systems. If the DB write is slow, the pipeline backs up.
Decision
Redis (live) + Kafka → Cassandra (history). Location Service writes to Redis synchronously, publishes to Kafka asynchronously. A Cassandra consumer appends to the location log. Ingestion is never blocked by the history write. Why Cassandra: append-only time-series, LSM-tree optimized for write throughput, horizontally scalable with no re-sharding.

New problem: global Redis or per-city?

Risky
One global cluster. A NYC surge slows queries for São Paulo. A failure takes down matching worldwide. Violates data residency requirements.
Decision
Shard by city. geo:drivers:nyc, geo:drivers:sf. Kafka topics also per city. Failure blast radius contained. Regulatory requirements met naturally.
Adaptive ping rate: A stationary driver pings every 30s; a driver approaching a pickup pings every 2s. Cuts write volume significantly without hurting matching quality.

5. Problem: Finding the Best Available Driver

The Problem

Given a pickup location and 5M drivers, find the best available driver nearby in under 100ms. "Best" is not just closest.

Spatial indexing

Workable
Geohash. Base-32 string encoding, prefix lookup. Simple. Problem: rectangular cells — diagonal neighbors are √2× farther than edge neighbors. Inconsistent proximity behavior near cell boundaries.
Decision
H3 (hexagonal grid, Uber's production choice). A hexagon's center is equidistant from all 6 neighboring hexagons — no diagonal-vs-edge inconsistency. Level 9 ≈ 175m resolution. Query pickup cell + 6 neighbors: candidate set shrinks from 5M to hundreds before any scoring.

Scoring — road ETA beats straight-line distance

A driver 800m away across a river might take 12 minutes. One 1.2km away on the same street: 4 minutes. Straight-line distance is meaningless in a city. Ranking must use road-network ETA.
FactorWhy
Road-network ETAPrimary signal. Modified Dijkstra with contraction hierarchies. Each query <50ms.
Driver ratingQuality signal, especially on premium tiers.
Acceptance rateAvoid drivers who frequently reject — they add latency to the cascade.
Vehicle type matchUberX request shouldn't go to an Uber Black driver if X drivers are nearby.

GPS accuracy

Naive
Use raw GPS directly. Urban canyon reflections cause 50–100m errors. Drivers appear in rivers and buildings. Matching degrades.
Decision
Map-matching via Hidden Markov Models — snaps raw GPS to the most probable road segment. Plus predictive positioning: extrapolate from last heading + speed. At 60 km/h, 5s = 83m gap; prediction reduces effective staleness to <10m.

6. Problem: One Driver, One Rider

The Problem

Two Dispatch Service instances simultaneously query Redis, get the same top candidate, and both attempt to assign them. Without coordination, one rider's driver never shows up.

Fails
In-memory lock per instance. Instance B has no knowledge of A's lock. Race condition guaranteed across processes. State lost on crash.
Better
DB compare-and-swap on driver status. available → outstanding_request atomically. Only one caller wins. Problem: timeout recovery lives in-memory — if the service crashes, the driver stays stuck in outstanding_request forever.
Decision
Redis SETNX with TTL. SET driver:42:lock 1 EX 10 NX — atomic, one winner, auto-expires after 10s whether the service crashes or the driver ignores the offer. No manual cleanup needed.
Decision

Acquire SET driver:{id}:lock 1 EX 10 NX before sending any offer. If lock fails, try the next candidate. If driver accepts within 10s → transition to on_trip. If they reject or time out → lock auto-expires, driver available again.

7. Problem: Service Crash Mid-Workflow

The Problem

Matching is a multi-step workflow: lock → offer → wait 10s → retry next driver → repeat. If Dispatch crashes mid-workflow, the rider waits indefinitely.

Fails
in-memory setTimeout. Timer state gone on restart. Rider stranded.
Better
Kafka delayed message. More durable. But Kafka has no native per-message delay — requires a separate delay service. Complex and fragile.
Decision
Temporal durable workflow. State persisted to durable storage. On crash, replays from the last checkpoint. Built-in sleep and timeout primitives model the 10s wait naturally.
The matching workflow in Temporal
workflow MatchRider(rideId):
  candidates = findNearbyDrivers(rideId)   // activity
  for driver in candidates:
    acquireLock(driver.id)                  // activity
    sendOffer(driver.id, rideId)            // activity
    result = waitForResponse(timeout=10s)   // durable sleep
    if result == ACCEPTED: return success
    releaseLock(driver.id)
  fail("NO_DRIVER_AVAILABLE")

Crash after sendOffer? Temporal replays from waitForResponse. No ride lost.

8. Problem: Rider Tracking Driver in Real-time

The Problem

During a trip, the rider sees the driver's position update every 5s. How does that update travel from the driver's phone to the rider's screen?

Wasteful
Rider polls every 5s. 315K concurrent trips × 12 req/min = 3.8M req/min of mostly empty responses. Up to 5s delay. Each wasted round-trip.
Decision
WebSocket — server pushes when an update arrives. ~50ms latency. Zero wasted requests. Connection opened when trip starts, closed when it ends.

New problem: routing pushes across 10M connections

New Constraint

At 10M connections we need ~1,000 stateful servers. If Dispatch sends an offer to the wrong server, the message is silently dropped. Which server holds a given user's connection?

Bottleneck
Central registry (Redis hash / ZooKeeper). Lookup on every push. Becomes a coordination chokepoint at high throughput. Adds a network hop to every message.
Decision
Ringpop. Consistent hashing maps each H3 cell ID to an owning node — any service computes the correct node locally, no lookup needed. SWIM gossip protocol propagates node health peer-to-peer. Transparent forwarding if a request hits the wrong node. No central coordinator.

9. API Design

Why a separate fare estimate step?

If we accept POST /rides { fare_amount }, a client can pass $0.01. Instead: POST /fare returns a server-side fare_id (stored in DB, 2-min TTL). Rider confirms with fare_id — server looks up the price, never trusting the client.

POST /fare → { fare_id, estimated_fare, eta }
Body: { pickup_lat, pickup_lng, dropoff_lat, dropoff_lng, ride_type }
POST /rides { fare_id } → { ride_id, status: "searching" }
Server looks up fare from DB, creates trip, publishes ride_requested to Kafka.
PATCH /rides/:id { action: "accept"|"reject" }
driver_id extracted from JWT — never trusted from request body.
POST /drivers/location { lat, lng, heading, speed }
Called every ~5s. driver_id from JWT.
→ Redis GEOADD + Kafka publish.

End-to-end: rider books a ride

1
Fare estimate
POST /fare → Fare Service calls Maps API → returns fare_id in PG (2-min TTL).
2
Rider confirms
POST /rides { fare_id } → Trip Service creates trip (SEARCHING), publishes ride_requested to Kafka.
3
Temporal workflow starts
Dispatch consumes event. GEOSEARCH Redis, score by road ETA.
4
Lock + offer
SETNX driver:{id}:lock EX 10. Notification Svc pushes via WS/APNs/FCM. Temporal sleeps 10s durably.
5
Driver accepts
Trip → DRIVER_ASSIGNED in PG. Rider gets WebSocket push with driver info.
6
Live tracking
Driver pings → GEOADD overwrites Redis + Kafka → Cassandra. Rider WS receives pushes via Ringpop routing.
7
Trip ends
Fare final computed, written to PG. Lock released. Both apps get TRIP_COMPLETED.

12. Failure Modes — Stress Testing the Design

2015 Uber outage: DB failover → 30-min global outage. The geo index was in the database. Fix: remove DB from the hot matching path entirely. The geo index now lives exclusively in Redis.
Redis crashes

Positions repopulate in 5s from driver pings. Trip state safe in PG. Locks expire via TTL — no stuck drivers.

Dispatch crashes mid-workflow

Temporal replays from last checkpoint. No dropped rides. Driver lock TTL auto-releases.

Driver ignores offer (10s timeout)

Temporal sleep completes. releaseLock called. Next candidate tried. Rider notified of updated ETA.

City-scale surge (concert, stadium)

Kafka absorbs the spike. Only that city's Redis shard is stressed. Other cities unaffected by geo-sharding.

ComponentPeak loadScaling approach
Location Service1M writes/secStateless, horizontal. Redis + Kafka sharded per city.
Dispatch Service350 matches/secStateless. Auto-scale on Kafka consumer lag.
WebSocket servers10M connections~1K servers @ 10K each. Ringpop handles routing.
PostgreSQL350 trip writes/secSingle primary + read replicas + PgBouncer.
Cassandra1M+ appends/secAdd nodes. RF=3. No re-sharding needed.
The three hard problems

1. 1M location writes/sec → Redis (live) + Kafka + Cassandra (durable)
2. One driver, one rider → Redis SETNX EX 10 NX
3. Matching survives crashes → Temporal durable workflow
Everything else follows from standard distributed systems patterns.
