Design Uber

A real-time ride-sharing platform: match riders with nearby drivers, track live location, manage trip lifecycle at global scale.

45 min interview Real-time / Geo-spatial 10M+ trips/day 1M location updates/sec
Interview Opening Move

Spend the first 3–4 minutes clarifying scope. Don't sketch anything yet. Ask: rider-side, driver-side, or both? Need payments? Surge pricing? Multi-city? Then explicitly state what you're designing vs. deferring.

1. Requirements

Functional (agree on these first)

Rider
  • Request a ride with pickup + dropoff
  • See fare estimate and ETA before confirming
  • Real-time driver location during trip
  • Cancel ride; rate driver after trip
Driver
  • Go online / offline
  • Receive, accept, or reject ride offers
  • Stream live GPS location every ~5s
  • Rate rider after trip

Non-Functional

Low Latency

Driver match delivered in <1 sec. Location updates every 5s.

High Availability

99.99% uptime. People depend on this for transport — failures are high-cost.

Strong Consistency

One driver must never be matched to two riders simultaneously.

Scalability

10M trips/day, 5M+ active drivers, global regions.

Eventual Consistency OK

Driver location can be a few seconds stale — acceptable for matching quality.

Real-time Push

Both apps need server-initiated updates — WebSockets, not polling.

Out of Scope

Payments Surge pricing algorithm Maps / routing engine Driver KYC & onboarding Fraud detection Driver navigation

3. API Design

Only design the APIs that reveal interesting decisions. The fareId pattern below is a common interview signal.

Step 1 — Fare estimate (before committing)
POST /fare
Body:  { pickup_lat, pickup_lng, dropoff_lat, dropoff_lng, ride_type }
→      { fare_id, estimated_fare, estimated_eta, surge_multiplier }

Why a separate fare step? Rider sees the price before booking. The fare_id is short-lived (~2 min TTL). When they confirm, we pass fare_id — not the client-computed price — to prevent price manipulation.

Step 2 — Create ride (commits to fare_id)
POST /rides
Body:  { fare_id }   ← server looks up fare from DB, never trust client price
→      { ride_id, status: "searching" }
Driver — accept / reject offer
PATCH /rides/:ride_id
Body:  { action: "accept" | "reject", driver_id }
→      { status, pickup_directions? }
Driver — stream location (called every 5s)
POST /drivers/location
Body:  { lat, lng, heading, speed }   ← no driver_id in body; extracted from JWT
→      200 OK

User identity comes from the session/JWT — never trust a client-provided ID in the body.

4. High-Level Architecture

Request Flow — Rider Books a Ride

1
Rider requests fare estimate
POST /fare → Fare Service calls Maps API for road-distance ETA. Returns fare_id (TTL: 2 min) + estimated price. Rider sees price before committing.
2
Rider confirms — ride created
POST /rides { fare_id } → Trip Service creates trip (SEARCHING) in PostgreSQL. Publishes ride_requested event to Kafka (partitioned by city).
3
Dispatch Service finds nearest drivers
Consumes Kafka event. Queries Redis Geo (GEOSEARCH) for available drivers within 5 km of pickup. Ringpop (consistent hashing) routes the query to the node owning that geo-cell — no scatter-gather needed.
4
Score candidates, acquire lock on best driver
Rank by: ETA (road-network, not straight-line) → rating → acceptance rate → vehicle type match. Acquire Redis lock SETNX driver:{id}:lock 1 EX 10. If lock fails (another request grabbed it), try next candidate.
5
Offer pushed to driver (10s window)
Notification Service pushes via WebSocket / APNs / FCM. Temporal workflow starts a 10s timer. On accept → transition driver to ON_TRIP, notify rider via WebSocket, update trip in PG. On reject/timeout → release lock, Temporal automatically retries with next candidate.
6
Live tracking during trip
Driver sends GPS pings → Location Service writes to Redis Geo (GEOADD overwrites, O(1)) + publishes to Kafka → Cassandra consumer appends to location history. Rider's WebSocket receives driver position every 5s.
7
Trip ends
Driver signals complete. Trip Service computes final fare (actual distance/time via Maps API). Writes to PG. Driver lock released. Both apps get TRIP_COMPLETED push.

5. Deep Dives

Pick 2–3 based on where the interviewer probes. Lead each with the problem statement before the solution.

5.1 — Handling 1M Location Writes/sec

This is the hardest scale problem. Walk through the evolution — interviewers want to see you arrive at the right answer, not just state it.

Bad
Write directly to a relational DB. At 1M writes/sec, a DynamoDB on-demand table alone costs $200K+/day. PostgreSQL with spatial indexes (PostGIS) can't sustain this write rate. And proximity queries on a full table scan are O(n) — unacceptable.
Good
Batch writes + geospatial DB (PostGIS / quad-tree index). Aggregate updates over 5–10s windows, then batch-insert. Proximity queries become O(log n) with spatial indexes. Problem: location data lags reality by the batch interval, and PostGIS still struggles with true 1M/s write throughput.
Great
Redis Geo as the live index + Kafka + Cassandra for history.
  • Redis GEOADD encodes lat/lng as a 52-bit integer in a sorted set. O(log n) write. GEOADD overwrites the previous position — no bloat, always current.
  • GEOSEARCH key FROMLONLAT lng lat BYRADIUS 5 km ASC COUNT 10 returns nearest drivers in sub-millisecond.
  • Location Service also publishes to Kafka. A separate Cassandra consumer appends to the location history log (audit trail, billing disputes).
  • Data is ephemeral in Redis — on restart, repopulates within 5s as drivers ping. No complex recovery needed.
Bonus point — adaptive pings: Driver app adjusts ping frequency based on speed and heading. A stationary driver pings less; one approaching a pickup pings more. Cuts unnecessary writes significantly without hurting matching quality.

5.2 — Geospatial Indexing: Geohash → S2 → H3

ApproachCell ShapeKey PropertyVerdict
Geohash Rectangles Encodes to base-32 string. Easy prefix lookups. Simple to implement. Edge artifacts at cell boundaries; cells distort near poles
Google S2 Quadrilaterals on cube-projected sphere Hierarchical cells as 64-bit integers. Used by early Uber for service region geofencing. Non-uniform cell area; square neighbors have unequal distances
H3 (Uber) Hexagons All 6 neighbors equidistant from center. Uniform area. Level 9 ≈ 175m resolution. Used in production Dispatch. Best for proximity — no edge-distance inconsistency

When a rider requests a trip: compute the H3 cell for pickup → query that cell + 6 neighboring cells → shrinks candidate set from 5M to hundreds before any ETA computation.

5.3 — Preventing Double Assignment (Distributed Lock)

Bad
Application-level locks. Multiple Dispatch Service instances can simultaneously select the same driver. Lock state is in-memory — lost on crash. Race conditions guaranteed at scale.
Good
DB status field transition (available → outstanding_request → accepted). Compare-and-swap in PostgreSQL prevents dual assignment. Problem: in-memory timeout tracking is lost on service restart — driver can get stuck in outstanding_request forever.
Great
Redis SETNX with TTL. SET driver:{id}:lock 1 EX 10 NX — atomic, only one caller wins, auto-expires after 10s whether the service crashes or the driver ignores the offer. No manual cleanup. Multiple Dispatch nodes can race safely.

5.4 — Driver Non-response & Workflow Orchestration

Bad
In-memory setTimeout. Works until the service restarts. Timer state lost → driver stuck, rider waiting indefinitely.
Good
Delayed Kafka message (delay queue). Publish a message with a future timestamp. Consumer processes it after the timeout. Better durability. Tricky to implement correctly; Kafka doesn't natively support per-message delays.
Great
Temporal (durable execution framework). The entire matching workflow is a Temporal Workflow — it persists state across crashes, has built-in sleep/timeout, and auto-retries activities. 
workflow MatchRider(rideId):
  candidates = findNearbyDrivers(rideId)   // activity
  for driver in candidates:
    lock = acquireLock(driver.id)            // activity
    sendOffer(driver.id, rideId)             // activity
    result = waitForResponse(timeout=10s)    // durable sleep
    if result == ACCEPTED: return success
    releaseLock(driver.id)
  fail("NO_DRIVER_AVAILABLE")
If the service crashes mid-workflow, Temporal replays from the last checkpoint. No dropped rides.

5.5 — Ringpop: Uber's Custom Consistent Hashing Layer

The problem: a driver's WebSocket is connected to a specific Dispatch node. If the matching engine routes an offer to the wrong node, it's silently dropped. Existing coordination tools (ZooKeeper, etcd) created centralized bottlenecks.

Ringpop solves this with:
  • Consistent hashing — maps each geo-cell (H3 cell ID) to an owning node. Any service can compute which node owns a given cell without a central registry.
  • SWIM gossip protocol — decentralized failure detection. Nodes gossip health status; no single point of coordination.
  • Transparent forwarding — if a request arrives at the wrong node, it's forwarded automatically to the correct owner.

Result: the Dispatch cluster is self-organizing and horizontally scalable with no coordination bottleneck.

5.6 — GPS Accuracy & Predictive Positioning

Urban Canyon Problem

In dense cities, GPS errors of 50–100m are common (building reflections). Solution: map-matching using Hidden Markov Models — snaps raw GPS coordinates to the most probable road segment, eliminating impossible positions.

Staleness Problem

With 5s update intervals, a driver at 60 km/h moves ~83m between pings. Solution: predictive positioning — use last known heading + speed to extrapolate current position. Reduces effective staleness from 83m to <10m.

8. Failure Modes & Scaling

Real 2015 Uber Outage: A database failover cascaded into 30 minutes of global downtime. The lesson: remove the database from the hot path entirely. Uber moved the geospatial index exclusively into in-memory (Redis / Ringpop nodes). The database is now cold storage only — not in the latency-critical matching path.

What Breaks First Under Load

Redis Geo under city-scale surge

Mitigation: Shard by city/region — geo:drivers:nyc, geo:drivers:sf. Each shard fits in RAM (~500 MB for 5M drivers). Ringpop handles routing to the correct shard without a central lookup.

Matching hotspot (concerts, airports)

Mitigation: Kafka absorbs the spike (consumer lag is OK — rides get processed in order). Auto-scale Dispatch Service replicas based on queue depth. Pre-position supply before known events.

Redis crash during active trips

Mitigation: Location data repopulates within 5s from driver pings. Trip state lives in PostgreSQL — unaffected. Driver locks expire naturally via TTL. Temporal workflows resume from checkpoint.

Dispatch Service crash mid-workflow

Mitigation: Temporal replays the workflow from the last durable checkpoint. The driver lock TTL auto-expires if not released, freeing that driver for other requests. No manual intervention.

Geo-Sharding Strategy

Each city operates as an independent cell: its own Redis geo index, Kafka topics (location.nyc), Dispatch Service pool, and Temporal namespace. Benefits:

  • Blast radius containment — NYC Redis failure doesn't affect London
  • Regulatory compliance — user data stays in region
  • Natural load isolation — peak demand in one city doesn't starve another

Cross-city boundary queries: Use scatter-gather across adjacent city shards. Uncommon (airports near borders), so the overhead is acceptable.

Closing statement for the interview: The three hardest problems in this design are (1) the 1M/sec location write throughput — solved by treating Redis as an ephemeral live index and Cassandra as the durable log; (2) preventing double assignment — solved with Redis SETNX TTL locks; and (3) resilient matching workflows across crashes — solved with Temporal.
