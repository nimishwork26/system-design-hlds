Designing a Stock Exchange

The hardest system to design correctly — not because of scale, but because correctness and fairness are legally mandated. Two orders for the same price must execute in the order they arrived, reproducibly, every time.

Distributed Systems Event Sourcing Low Latency Financial Systems
In-Memory Order Book Sequencer Pattern LMAX Disruptor Market Data Fan-out 10 µs matching latency

1. Requirements

Functional
  • Place, cancel, and modify limit & market orders
  • Match buy and sell orders at the best available price (price-time priority)
  • Broadcast real-time market data: last trade price, bid/ask, order book depth
  • Provide order status updates to traders (filled, partial fill, cancelled)
  • Pre-trade risk checks: position limits, buying power, circuit breakers
Non-Functional
  • Latency: <10 µs order-to-match on hot path
  • Throughput: 1M+ orders/sec at peak
  • Fairness: strict price-time priority, legally enforceable
  • Durability: zero order loss — every accepted order must execute or be explicitly cancelled
  • Availability: 99.99% during market hours (09:30–16:00 ET)
Out of Scope
  • Settlement and clearing (T+2 via DTCC — a separate regulated entity)
  • KYC / account onboarding
  • The routing engine (smart order router, dark pools)
  • Margin calculation and collateral management
  • Market surveillance and fraud detection

2. Capacity

Only the numbers that create hard architectural problems.

MetricNumberWhy it creates a problem
Peak order throughput 1,000,000 orders/sec Every relational DB tops out at ~10K writes/sec with index maintenance. We are 100× over that limit.
Matching latency target <10 microseconds One network round-trip to a DB takes 500–2,000 µs. Any network call on the hot path is an instant 100× miss.
Active symbols ~8,000 (NYSE) Each symbol needs its own isolated order book — shared state between symbols creates contention for no benefit.
Market data subscribers ~1,000,000 Every trade and quote update must reach all subscribers. A naive push-to-all is an N×M fan-out problem.
Order book depth per symbol ~100 price levels Each level is a FIFO queue of orders. The data structure choice determines whether match is O(1) or O(n).
Messages per day ~10 billion The event log (WAL) that enables crash recovery must handle this append volume durably.
The key insight: Unlike most systems where you can trade latency for throughput, a stock exchange demands both simultaneously. 1M orders/sec at 10 µs — not 1M orders/sec or 10 µs. This combination eliminates every solution that touches a network or disk on the critical path.

3. Start Simple

Traders submit buy/sell orders to an API server. The server writes the order to a database and queries for matching orders (best ask ≤ best bid). On a match, it updates both orders and records a trade. Simple enough.

flowchart LR Trader -->|POST /orders| API["API Server"] API -->|INSERT order| DB[("Orders DB\n(PostgreSQL)")] DB -->|SELECT best match| API API -->|UPDATE matched orders| DB API -->|Notify| Trader

Where the naive design breaks

Break #1 — The database can't match at microsecond speed

Matching one order requires at minimum: SELECT best opposite order + UPDATE matched quantity + INSERT trade record = 3 round-trips × 500 µs each = 1.5 ms minimum. Target is 10 µs. We are 150× too slow before even considering 1M orders/sec write pressure.

Break #2 — Two servers pick the same counterparty order

Scale to multiple API servers. Two servers concurrently find the same best ask, both decide to match against it, both UPDATE it. The same shares are sold twice. Database-level row locking "fixes" this but serializes every match through one DB lock — throughput collapses to ~1K matches/sec.

Break #3 — Market data fan-out is an N×M explosion

Every trade and quote change must be pushed to ~1M subscribers. If the matching server is also responsible for pushing updates, a slow subscriber (network congestion, overloaded client) blocks the matching loop. One bad client takes down the entire exchange.

Break #4 — Server crash = order book lost

The matching logic runs on stateless API servers; the database is the "order book." After a crash, open orders still exist in the DB — but mid-flight orders (received but not yet persisted) are silently lost. In a fast market, thousands of orders can be in-flight at any instant.

4. Fix #1 — In-Memory Matching Engine

The Problem

Any database round-trip (500–2,000 µs) on the match path makes the 10 µs target physically impossible. The order book must live somewhere with nanosecond access time: process memory.

Fails
PostgreSQL + price-time index — ACID, MVCC, already in the stack. Seems safe and correct.
Best-case 3 round-trips per match at 500 µs each = 1.5 ms. At 1M orders/sec, matching falls 150,000× behind ingestion. Index maintenance under 1M writes/sec causes cascading write stalls. No path to 10 µs.
Fails
Redis sorted set per symbol — in-memory, O(log n) inserts and range queries. Network call is only ~100 µs.
Still 10× too slow. Redis Lua scripts can't atomically "match and execute" across two sorted sets (buy side + sell side) without a custom module. No concept of FIFO within a price level — price-time priority is impossible.
Decision
In-process order book — a price-level map with FIFO queues — the order book lives entirely in the matching engine's heap memory. Zero network. Zero disk. O(1) match check (compare best bid vs best ask). O(1) insert at a known price level (append to FIFO queue).
Decision — In-Memory Order Book

Buy side: TreeMap<Price, Queue<Order>> sorted descending (highest bid first). Sell side: TreeMap<Price, Queue<Order>> sorted ascending (lowest ask first). Match check: peek at best_bid.price ≥ best_ask.price → O(1). Execute: dequeue from both FIFO queues, preserving time priority exactly. Each symbol gets its own matching engine thread — no shared state, no locks.

Why single-threaded per symbol?

✕ Multi-threaded matching per symbol

Two threads could match the same order simultaneously. Fixing this requires a mutex on every order book operation. Acquiring a mutex takes 50–200 ns — already 5–20× over the 10 µs budget for just the lock. Contention under load makes it worse.

✓ One thread per symbol

No shared mutable state between threads. No locks. No cache-line contention. The matching thread processes orders one at a time in strict arrival order. Correctness falls out of the model — you can't have a race condition with one thread.

The "aha" moment: The matching engine is single-threaded NOT because we don't have cores, but because adding parallelism requires locks that cost more nanoseconds than the match itself. Eight symbols → eight threads, each saturating one core at near-100% utilization. NYSE runs ~8,000 symbols on a cluster of single-threaded matching engine processes.

5. Fix #2 — The Sequencer

The Problem

Orders arrive from thousands of concurrent clients. The matching engine is single-threaded — it processes one order at a time. Which order does it process first? If two orders arrive within the same microsecond from different gateway servers, and the gateways disagree on ordering, then two replicas of the matching engine produce different trade results. The system has split-brain at its most critical component.

Fails
Database auto-increment sequence number — the DB assigns a monotonically increasing ID before the order reaches the matching engine.
Requires a DB round-trip per order (1–5 ms). At 1M orders/sec, the sequence DB becomes the bottleneck — and it's on the critical path. Also: two DB instances for HA means two sequence generators, which means gaps and possible non-monotonicity.
Partial
Kafka topic with a single partition per symbol — Kafka guarantees ordering within a partition. Clients publish directly to Kafka; matching engine consumes.
Ordering is guaranteed, but the sequence number is assigned by Kafka at write time — which is after the client's network trip to the broker. Two clients publishing "simultaneously" have their order decided by whichever packet arrives at the Kafka broker first. This is acceptable fairness for most exchanges, but the Kafka broker itself becomes a network-latency bottleneck.
Decision
Dedicated single-threaded Sequencer service — a single process that receives orders from all gateways, stamps a monotonically increasing sequence number, and publishes to the sequenced log (Kafka, single partition per symbol). The matching engine reads from this log in strict order.
Decision — Sequencer + Sequenced Log

The Sequencer is the single serialization point for all order events. It is the boundary between "concurrent world" (many clients) and "ordered world" (single-threaded matching). Once an order has a sequence number, the system is deterministic: given the same log, the same trades result every time — enabling both crash recovery and audit replay with zero extra work.

1
Order Gateway receives order from trader
Pre-trade risk check (position limits, buying power). If passes, forwards to Sequencer.
2
Sequencer stamps sequence number
Single thread. Atomically increments a counter, attaches seq=1000042 and timestamp. Publishes to Kafka topic orders.AAPL partition 0.
3
Matching Engine consumes from Kafka in order
Reads orders.AAPL from last committed offset. Processes seq=1000042 before seq=1000043. Always. No matter what.
4

Topic trades.AAPL. Every filled order, every partial fill, every cancel — all events go here. This is also the write-ahead log (see Fix #4).
Fairness guarantee: NYSE and NASDAQ have implemented "speed bumps" (IEX's 350-microsecond coax cable delay) specifically to give sequence numbers to orders based on receipt time, not network advantage. The Sequencer is what makes this physically enforceable.

6. Fix #3 — Market Data Distribution

The Problem

Every trade and every order book change must reach ~1,000,000 subscribers as fast as possible. If the matching engine is responsible for pushing updates, a single slow subscriber (network congestion, GC pause, overloaded app) causes the matching loop to stall. One bad client can freeze the entire exchange.

Fails
Matching engine pushes directly to all subscribers via WebSocket — no middleware, lowest latency at first glance.
The matching engine now manages 1M open connections. A GC pause on the matching engine thread stalls both matching AND delivery. Slow subscribers block the event loop. This architecture conflates the exchange's two completely different workloads.
Partial
Kafka → WebSocket fan-out tier — matching engine publishes to Kafka, a fleet of WebSocket servers consume and push to clients. Decoupled.
Each WebSocket server handles ~50K concurrent connections. At 1M subscribers you need 20 servers. Now you need a routing layer to know which server holds each subscriber's connection. Operational complexity and another hop of latency.
Decision
Ring buffer (LMAX Disruptor) → Kafka → Market Data Service — the matching engine writes trade events to a lock-free ring buffer (zero heap allocation, zero GC pressure). A separate publisher thread reads from the ring buffer and writes to Kafka asynchronously. The Market Data Service fans out to subscribers.
Decision — Two-Tier Market Data

Internal (matching → Kafka): LMAX Disruptor ring buffer — lock-free, cache-line-aligned, zero GC. The matching engine never blocks on a slow subscriber. External delivery (two tiers by client type):
• Retail / API clients: WebSocket via Market Data Service — tolerate 10–50 ms latency, manageable connection count.
• HFT co-location clients: UDP multicast on the exchange's private network — no TCP handshake, no retransmit, best-effort sub-millisecond delivery. HFT clients are expected to handle packet loss with their own gap-fill logic.

Why UDP for HFT? TCP's reliable delivery requires acknowledgements, retransmits, and per-connection state. At 1M messages/sec across 100 co-location clients, this is 100M ACKs/sec just for one symbol. UDP multicast sends one packet that all subscribers receive simultaneously — the "cost" per additional subscriber is zero bytes of extra bandwidth.

7. Fix #4 — Event Sourcing & Crash Recovery

The Problem

The matching engine holds the full order book in process memory. On crash, all in-flight orders (received by the Sequencer but not yet confirmed as processed) are ambiguous — did they execute? The exchange cannot tell a trader "we're not sure if your order filled." That is not a valid system state.

Fails
Checkpoint the order book to disk every N seconds — a periodic snapshot that can be restored on restart.
Up to N seconds of order events are lost on crash. In a fast market, N=5 seconds = thousands of trades lost. Re-processing the last N seconds of orders with current prices produces different trades than the original — prices have moved. Regulatorily unacceptable.
Partial
Synchronously write each order to a durable DB before matching — durability first, then match.
Adds a DB round-trip (1–5 ms) to every order before matching. We are back to Break #1. The hot path is throttled to DB write speed, not matching engine speed.
Decision
The Kafka sequenced log IS the write-ahead log — every order was already durably written to Kafka by the Sequencer before the matching engine saw it. Crash recovery = restart the matching engine and replay from the last committed Kafka offset.
Decision — Event Sourcing via Kafka Replay

The matching engine is a pure function of its event log: state = reduce(events[0..N]). This is event sourcing in its simplest form. On crash: consume all unprocessed events from Kafka starting at the last committed offset. The matching engine is deterministic — same inputs, same outputs, same order book state. Recovery takes ~30 seconds for 1M events at replay speed — acceptable for a market that can suspend for a technical halt.

What gets persisted and where

  • Kafka (sequenced log): every order event with its sequence number — the immutable source of truth
  • PostgreSQL: current order status per order ID — allows traders to query "is my order open?" without replaying the full log
  • Cassandra: all executed trades — append-only, partitioned by symbol + date, clustered by timestamp. Historical queries: "show all AAPL trades today."
The elegance of this design: The Sequencer (Fix #2) was added to solve ordering. The Kafka log it writes to gives us event sourcing for free. The Market Data Service (Fix #3) reads the same Kafka log. Three problems solved by one component: the sequenced Kafka topic.

8. Risk Engine & Order Management

The Problem

A trader submits an order to buy 10M shares of AAPL — more than their account balance allows. If the matching engine processes this before checking limits, the trade executes. Unwinding it requires calling the counterparty, regulatory notification, and potentially market-moving cancellations. Pre-trade risk is not optional.

Pre-trade risk (synchronous, on the gateway)

Every order passes through the Risk Engine before it reaches the Sequencer. The Risk Engine checks:

  • Buying power: cash + margin available ≥ order value (Redis hash lookup — O(1))
  • Position limits: existing position + order size ≤ regulatory max
  • Price sanity: limit price within X% of last trade (prevents fat-finger orders from moving the market)
  • Circuit breakers: symbol-level and market-level halt flags in Redis
Decision — Risk State in Redis

Position and cash balances live in Redis (hash per account). The Risk Engine does sub-millisecond reads. Updates happen asynchronously as trades settle: the OMS consumes trade events from Kafka and increments/decrements Redis balances. There is a small window of inconsistency between trade execution and balance update — this is acceptable and standard practice. Brokers hold regulatory capital buffers that cover this window.

Order Management Service (OMS)

The OMS bridges the matching engine and the trader. It consumes all order events from Kafka and:

  • Updates order status in PostgreSQL (open → partially_filled → filled)
  • Updates account balances in Redis on fill
  • Sends execution reports to traders via the Order Gateway WebSocket
  • Handles cancel-on-disconnect (if trader WebSocket drops, cancel open orders)

9. API Design

Only the endpoints with non-obvious design choices.

Order submission — why not REST?

✕ REST POST /orders

Each order requires a new TCP connection or connection-pool slot. HTTP headers add 200–500 bytes of overhead per order. At 1M orders/sec from institutional clients, header parsing alone consumes significant CPU. Response model assumes synchronous execution — but matching is asynchronous.

✓ FIX Protocol over TCP (or WebSocket for retail)

FIX (Financial Information eXchange) is the industry standard. Binary-ish text protocol, persistent connection, no headers per message. Institutional clients: raw FIX TCP. Retail / web clients: JSON over WebSocket. Both are persistent bidirectional connections — execution reports arrive on the same connection without polling.

Key endpoints

OperationMessage TypeKey Design Choice
NewOrderSingle FIX D / WS JSON client_order_id is client-generated for idempotency. Server assigns exchange_order_id after sequencing. Client ID enables dedup on network retry without re-submitting.
OrderCancelRequest FIX F Cancel by exchange_order_id, not symbol + price. Price-level cancels would require scanning the book — O(n) instead of O(1) hash lookup by ID.
ExecutionReport FIX 8 (server → client) Server-initiated. Sent on: new order ack, partial fill, full fill, cancel confirm, reject. The client never polls — it receives reports asynchronously on its open connection.
Market Data Subscribe WS / UDP multicast Subscription granularity is per-symbol, not per-trade. Clients declare symbols they want. Market Data Service maintains per-symbol subscriber lists. Symbol-level filtering happens server-side.
Idempotency

The client_order_id field is critical: if the client sends an order and the network drops before receiving the ack, the client can safely re-send with the same client_order_id. The gateway deduplicates on this field — the order is sequenced exactly once. Without this, network retries cause duplicate orders.

Every component arrived through a break point. The Sequencer and the Kafka event log are the load-bearing components — every other piece depends on the guarantee they provide.

11. Data Models

StoreWhat lives thereWhy this store
In-process memory (ME) Live order book: price-level maps per symbol Zero network, zero disk. O(1) match. The only store that can meet 10 µs. Ephemeral — rebuilt from Kafka on restart.
Kafka (sequenced log) Every order event with sequence number Durable, ordered, replayable. The write-ahead log. Also the market data feed source. Three uses, one component.
PostgreSQL Order status: order_id, symbol, state, filled_qty ACID for correctness. Traders query "is my order open?" — ~350 reads/sec, well within limits. Updated by OMS asynchronously off the trade event stream.
Cassandra Trade history: symbol, timestamp, price, qty, buyer_id, seller_id Append-only time-series. LSM-tree optimized for this pattern. Partitioned by symbol+date, clustered by timestamp. Historical queries for compliance and analytics.
Redis Account balances, position totals, circuit breaker flags Sub-millisecond reads for pre-trade risk checks. Hash per account: HGET account:42 buying_power. Updated asynchronously as trades settle.
kdb+ Full tick data: every quote and trade with nanosecond timestamps Column-oriented time-series DB purpose-built for financial data. Used by quant research and compliance — not on the trading path.

12. Failure & Scale

Stress-testing the key decisions

Failure ScenarioWhat happensWhy it's safe
Matching engine crashes Failover instance replays Kafka from last committed offset Matching engine is deterministic — same Kafka log = same order book state. Recovery ~30s. Exchange declares technical halt, resumes when recovery is confirmed.
Sequencer crashes Standby Sequencer takes over from last assigned sequence number (stored in ZooKeeper) The standby reads the last sequence number from durable state. There is a gap in sequence numbers (the lost window) — the matching engine skips the gap and logs it for audit. Orders in-flight are re-submitted by clients on timeout.
Kafka broker failure Kafka replication (RF=3) — failover to replica within ~10 ms Sequencer's Kafka producer blocks until the leader replica confirms write. No event is acknowledged without durability. ISR (in-sync replicas) guarantee no data loss on leader failure.
Market volatility surge (circuit breaker) Risk Engine sets a halt flag in Redis; all gateways reject new orders for that symbol The halt flag is checked on every order submission — O(1) Redis read. No change to the matching engine required. Halt resolves within seconds once volatility subsides.
Redis crashes (risk state lost) Risk Engine falls back to conservative limits (reject all orders above a low threshold) Redis positions are rebuilt from Kafka trade events by OMS on restart. During the ~5 min rebuild window, conservative limits prevent large orders that could cause harm.

Scale-out strategy

  • Matching engines: one process per trading symbol. 8,000 symbols → 8,000 processes across a cluster. Horizontal scale is trivially additive.
  • Sequencers: one per symbol (same partitioning as matching engines). Each is a single thread — if throughput exceeds ~2M orders/sec for one symbol (only possible in extreme volatility), split the symbol's order book by price range.
  • Market Data Service: fan-out tier is stateless and horizontally scalable. Add servers proportional to subscriber count. WebSocket servers are routed by consistent hashing on subscriber ID.
  • Kafka: partition-per-symbol. Add brokers to increase total parallelism. Replication factor 3 for all exchange-critical topics.
The 2010 Flash Crash: The Dow dropped 1,000 points in minutes. Root cause: a large sell order triggered cascading stop-loss orders. A properly implemented circuit breaker (halt trading when price moves >5% in <5 minutes) is the only safe mitigation. The Sequencer's sequence log is what allows post-incident forensic replay to determine the exact causal chain.
